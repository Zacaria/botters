# Online accounts

## Boundary

Online identity uses Better Auth 1.6.33 with the Convex component: email/password, verified email, password reset and Google sign-in. Better Auth owns password hashing, verification and reset tokens; the application never handles raw credentials outside the auth proxy. No account merging, legacy-name migration, paid inference, paid plan or new database. Offline `server.js` and its MCP path remain login-free.

Chosen over Convex Auth because Better Auth provides the required credential/reset/verification flow with a Node-compatible handler and fixed owned-domain callback through an ordinary same-origin proxy. Its official Convex adapter uses the existing project without introducing a separate identity database or framework migration. Application authorization still checks the live server session rather than trusting a client-supplied account ID or adding a second JWT system. The original PvP release's display-name/session-expiry descriptions are historical; this document defines the account candidate's replacement boundaries. Version 1.6.33 avoids the pre-account-hijacking advisory affecting versions below 1.6.22.

The Vercel `/api/auth/*` proxy forwards only supported Better Auth routes to the existing Convex deployment's HTTP actions. Better Auth's canonical base URL is `https://botters.havesomecode.io`; exact Google callback: **https://botters.havesomecode.io/api/auth/callback/google**. No paid Convex domain is needed. Owned-origin cookies are HttpOnly, Secure, SameSite=Lax. The older Vercel alias keeps its public descriptive homepage; account links explicitly use the owned origin. Online play requires login. Preview never uses production identity or a production OAuth callback. Local tests use isolated auth configurations.

## Identity and authorization

A verified Better Auth user ID, obtained by the server from the session cookie (never the request JSON), owns a durable account-to-game-session record. Reloads and other devices create new human capabilities to the same account session; human capabilities additionally require that account's live auth session. Unauthenticated online game requests return 401; only auth, descriptive pages and the limited agent pairing handshake are public. Neither a name change nor an email/name collision claims or merges existing Elo/history. Existing display-name ratings are left untouched and excluded from the verified board. New ratings use account ID plus setup, not a display name.

MCP starts a ten-minute pairing request with a private polling capability and a separate public approval identifier. It receives no browser/account token. The signed-in human explicitly approves the named setup in the browser. Approval binds that agent-only capability to their game session and current delegation version. Replacement/revocation invalidates older delegates; an agent cannot edit human profile, join rooms, mint human capabilities, pair another agent or change account state. Expired/unapproved/revoked agents cannot play. Anonymous pairing attempts are rate-limited. Sign-out revokes the Better Auth cookie session; previously issued human capabilities cannot work without a live owner cookie. Agent revocation is a separate visible control so sign-out does not silently terminate an approved agent's ongoing match.

History is attached to the stable account session; guest history is not merged. Ratings are casual even for verified accounts: a verified sign-in does not prove one account per human or prevent collusion. Only matches between distinct verified accounts affect the verified board; house/self matches do not.

## Cookie-bound live transport (activation candidate)

The control website stays same-origin with Better Auth. With `liveExchange` enabled, `/session` derives the real auth-session ID and expiry from the server-side cookie check and issues a 60-second, single-use live ticket. The ticket contains no provider credentials and is sent in a POST body to the live host. An internal Convex mutation validates that real session and verified user again, consumes the ticket atomically and binds the human capability to a host-only HttpOnly live cookie. Cross-origin requests include credentials; exact-origin CORS permits credentials, never wildcard origins. The browser's Better Auth cookie and proxy secret never reach the live host; its auth-session identifier is used only by the server-side durable authorization path and is omitted from client responses. The live authorization subscription validates the same auth session and verified user, with explicit expiry and the existing fail-closed 90-second refresh ceiling. Logout or password reset invalidates human HTTP and WebSocket access; separately approved agents retain their established revocation policy. Unexchanged, stolen or expired human bearer tokens fail without their bound cookie, including reservation and WebSocket admission.

This is not production acceptance evidence. `BOTTERS_REQUIRE_ACCOUNT=1` selects the live account boundary only after its reviewed candidate is released; production remains anonymous until the provider/UI acceptance checks below pass. Isolated browser tests run two loopback origins with real Better Auth sessions, captured mail, Colyseus WebSockets and a fixture durable adapter; actual Convex component tests separately exercise atomic ticket consumption and session revocation. Neither fixture proves Google consent or external email delivery.

## Configuration and release

Convex server-only variables: `BETTER_AUTH_SECRET`, `SITE_URL`, existing `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET`, `RESEND_API_KEY`, `AUTH_EMAIL_FROM`, `BOTTERS_AUTH_PROXY_SECRET`. Vercel server-only: the same `BOTTERS_AUTH_PROXY_SECRET`, `BOTTERS_AUTH_SITE_URL` (existing deployment's `.convex.site` URL), `BOTTERS_AUTH_ORIGIN` (owned origin). The two existing Google variables are mapped directly, not renamed. Never expose provider keys to clients, logs, fixtures or artifacts. Email sending must use an already-authorized verified domain; no invented sender or new paid resource. Missing configuration fails closed. No email change or automatic account linking endpoints are exposed.

The direct Convex HTTP auth endpoint rejects requests without the proxy secret. Only Vercel supplies the client IP input. The outer Vercel boundary uses the existing durable CAS store to enforce atomic fixed-window per-IP limits: five password attempts/minute, five signups/ten minutes, three reset or verification emails/ten minutes, and thirty other auth requests/minute. Better Auth's own database limits are secondary: the current Convex adapter does not provide atomic rate increments, and the library cleanup window must be at least the longest custom window (600 seconds). Neither concurrency nor touching another endpoint clears the outer limits. Only rules/account discovery, limited pairing and auth endpoints are public; game state is not. Online state uses the cookie-bound Colyseus exchange above, not SSE. Local offline SSE remains login-free. Delegation revocation is rechecked on every agent request.

Preview on an unrelated hostname cannot reuse the owned-origin production auth cookies or proxy. Until isolated preview provider configuration is supplied, preview sign-in links explicitly open the owned production site; this is not a preview auth acceptance pass. The loopback-only `scripts/auth-dev.js` fixture exercises the real library with captured emails and no external sending, never production identities. `npm run test:auth:browser` covers that fixture; the Convex component/proxy suite is separate.

Before production activation: integrate reviewed public homepage/privacy/terms/contact pages; verify Google branding/domains/credentials and actual email delivery; run real Google and email/password/reset round trips, expired/replayed reset/verification link checks, logout, pairing/revocation, two-account reconnect/history/Elo and ordinary PvP regression. Unit tests and isolated Better Auth HTTP tests establish implementation behavior but are not evidence of a real provider login. Stop only the missing provider action if configuration/access is unavailable; preserve the verified candidate and exact operator prerequisite.
