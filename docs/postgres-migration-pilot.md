# PostgreSQL account migration pilot — historical experiment

Superseded by the direct [Cloudflare replacement](cloudflare.md), with no data import and no parallel PostgreSQL repair. The evidence below is retained, not a current prerequisite.

The deployed website still uses Vercel and Convex; the Colyseus service runs on Lightsail. This branch does not cut over either service. The intended account database is PostgreSQL alongside the eventual Node service on Railway; keep the existing live simulation and Better Auth policy. The isolated pilot uses synthetic accounts and a disposable loopback PostgreSQL database only.

The PostgreSQL record store uses a transaction-scoped advisory lock per namespace to serialize CAS commits, including guards on absent and expired keys and leaderboard projections. Its table is independent of Better Auth; the candidate HTTP and live entry points can explicitly use it with the same namespace. Expired rows remain invisible and can be replaced. `expire(limit)` removes at most the requested number of expired rows (1–128, default 128) in the current namespace, without removing permanent or unexpired rows; it must be scheduled and monitored before production. A single namespace lock favours correctness over throughput and requires production load qualification.

The loopback-only browser fixture can also use PostgreSQL for both Better Auth and the record store when `BOTTERS_TEST_POSTGRES_URL` is set. Run `BOTTERS_TEST_POSTGRES_URL=postgresql://... npm run test:auth:browser` on a disposable local database. It creates and drops a random test schema on normal shutdown and captures email in memory. Its in-process authority and exchange remain test-only; they do not establish safe production revocation across processes. An abrupt kill can leave the synthetic schema behind. Do not use a shared database.

The pilot exercises Better Auth's real PostgreSQL adapter: account creation, email verification, password sign-in, session persistence across application restarts, and sign-out. The candidate entry points wire PostgreSQL into HTTP and live authority; end-to-end behavior still requires integrated qualification. It does not import existing accounts, enable Cloudflare hosting, Google consent, production email, or cutover. The existing Convex account IDs, password hashes, sessions, game history, ratings, agent grants, atomic single-use tickets and revocation semantics must be reconciled before a real migration; no account merging or personal-data transfer is authorized here. Existing IP-based durable rate limits and origin checks must survive the hosting change. A database schema initialized for tests is not a production migration.

Run `BOTTERS_TEST_POSTGRES_URL=postgresql://... node --test test/postgres-auth.integration.test.js` against a disposable local PostgreSQL database. The test creates and drops an isolated schema inside that database; never point it at a real or shared database. Mail is captured in memory and no message is sent. Without that explicit test URL, the integration test is skipped.

The PostgreSQL authority snapshot reads the live capability and game owner together. For humans it also checks the verified Better Auth session and bound cookie; for agents it checks the owner's current agent version without tying the grant to a human login session. Missing, expired, malformed or revoked grants are refused, and the lease is bounded by relevant expirations. The live entry point can use this adapter to poll the snapshot every 500 ms by default, with a two-second maximum lease from the start of each query; failed, late or stalled refreshes cannot extend the lease. Revocation is therefore bounded, not instantaneous. Its database load has not been qualified. Adapter tests alone do not prove an authenticated game journey.

The isolated PostgreSQL ticket exchange validates the verified Better Auth account, its session and the matching game owner inside one transaction. Ticket, capability and owner expiry must be checked again after any database lock wait, before the exchange is committed. It consumes each ticket once and binds the resulting cookie proof; concurrent exchanges have at most one winner. The live entry point can use this exchange and the polling authority; the integrated journey and its revocation latency still require verification. Run `BOTTERS_TEST_POSTGRES_URL=postgresql://... node --test test/postgres-live-exchange.integration.test.js` against a disposable loopback-only database; the test creates and removes its own synthetic schema.

Before any production transition, preserve current website deployment and live image rollback handles, obtain a fresh no-active-match gate, qualify an exact reviewed candidate with both stores and the real authenticated gameplay journey, and receive specific authorization for personal-data transfer and any provider mutation. Rollback must retain writes made after cutover or explicitly prevent them; merely pointing back at the old site is not sufficient.
