## Server-only configuration

| Variable | Meaning |
| --- | --- |
| `AUTH_EMAIL_PROVIDER` | `cloudflare` selects Cloudflare Email Sending. Omitted or `resend` preserves the existing Resend path for staged activation and rollback. Any other value fails before network access. |
| `AUTH_EMAIL_FROM` | Sender on the approved, onboarded sending domain. For Cloudflare use a plain mailbox, e.g. `no-reply@example.test`, not a display-name string. Choose the real domain only during authorized activation. |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare account identifier: exactly 32 hexadecimal characters; not a zone ID or a URL. |
| `CLOUDFLARE_EMAIL_API_TOKEN` | Secret API token with Email Sending permission on the intended account. Never put its value in Git, public build settings, logs or evidence. No token is created by this task. |
| `RESEND_API_KEY` | Existing secret needed only for the Resend path. Retain securely until migration and rollback checks are complete. |

These variables belong in whichever server runs auth (Convex currently; the PostgreSQL control server after its separate migration). They are not browser settings and do not change Google, proxy, origin or database variables. An existing named Resend sender must be replaced by a plain Cloudflare mailbox at activation; preserve its original value for rollback.

## Request, refusal and tracking

Cloudflare receives one POST to `https://api.cloudflare.com/client/v4/accounts/{account_id}/email/sending/send`, with Bearer authorization and only `from`, `to`, `subject`, `text`. Redirects are refused. The existing eight-second timeout covers the request and response body. No automatic retry and no fallback to Resend: an interrupted response may already have accepted an email, so retry/fallback could duplicate token messages.

Missing provider credentials, sender or a malformed account ID fail before the request. HTTP failures (including 401/403, 429 and 5xx), network/timeout failures, invalid JSON, `success: false`, nonempty API errors, permanent bounces, suppressions and missing/contradictory recipient outcomes fail with the generic `Email delivery is unavailable.` error. Provider response bodies, addresses, links and secrets are not logged or included in errors. The existing auth framework remains responsible for its public failure/anti-enumeration behavior.

For the one requested recipient, exactly one `delivered` or `queued` outcome is accepted. The internal result exposes `provider`, `status` and `messageId` when the REST API supplies `message_id`; older documented response examples omit it. `queued` is not delivery, and `delivered` means provider-reported delivery to a mail server, not inbox placement. Better Auth does not persist this result or install a webhook in this increment.

For an authorized real pilot, correlate the returned message ID (when available) and time with Email Service Activity log/GraphQL analytics. Check Sent, Delivered, Delivery failed, Rejected and Failed separately; inspect inbox and redeem the actual link. Do not record recipients, message bodies, reset tokens or full auth URLs in engineering evidence. Cloudflare's documented default email preview retains message bodies, including auth links, for about seven days on new sending domains: review/disable preview before any authorized auth pilot, rather than silently creating a new token archive.
